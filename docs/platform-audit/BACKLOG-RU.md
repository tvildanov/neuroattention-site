# Порядок внедрения и приёмка

Статус 21 ноября: в PR #212 реализованы серверные проверки A, персональная транзакционная запись B и короткий ввод/исходник/история C. Объединённая API-матрица проходит; браузерная проверка и выпуск ожидаются. Семейная идемпотентность, полный новый кабинет и остальные пакеты ещё не завершены.

Изначальный план: все пакеты ниже запланированы; реализация и production-релиз не входят в коммит аудита. Очерёдность основана на зависимостях. Оценки стоимости/сроков требуют проверки изолированной среды и текущих тестов; обещания «за один промпт» не давать.

## Пакет A. Зафиксировать среду и доступ

Приоритет P0. Закрыть вопросы F01/F07 и проверки раздела 5 аудита до расширения аудитории.

- Создать изолированную тестовую БД/среду без копирования личных production-записей.
- Синтетические роли: клиент без программы, клиент с программой, второй клиент, специалист, администратор. Полномочия выдаются через штатный серверный механизм, не путём подмены токена/браузерного UI.
- Изолировать миграции от публичного запроса; проверить course completion и RTC membership.
- Воспроизвести существующий CI с PGlite и текущие браузерные сценарии; фиксировать точный commit.
- Для платного пути нужны штатный тестовый доступ либо предоставленная владельцем тестовая сессия. Пароли не хранить в отчётах.

Готово, когда матрица разрешённых/запрещённых действий проходит для всех ролей и существует воспроизводимый запуск. Не расширять роль реального пользователя ради аудита.

## Пакет B. Подтверждённая запись

Приоритет P0/P1; зависит от A для выпуска. Один PR на серверный контракт и клиентскую форму либо совместимые последовательные PR.

- Запись с operation_id и возвратом record_id; явно определить атомарный минимум.
- Повтор запроса не увеличивает число записей/счётчик и не выдаёт повторное вознаграждение.
- nmSaveSurvey ожидает результат; состояние формы сохраняется при ошибке, успех появляется только после подтверждения.
- Разделить подтверждённое сохранение исходника и готовность графа. Повторять/сверять проекции.
- Кэш привязать к пользователю. Проверить выход, вход второго пользователя, истёкший token, изменение домена.

Приёмка: 20 повторов одного operation_id, 401, 403, 500, timeout после фактической записи, reload во время отправки, частично недоступная проекция. Во всех случаях исходник не теряется и не дублируется. Числа — требования к будущему тесту.

## Пакет C. Один цельный интерфейсный сценарий

Приоритет P1. В прототипе не требовать готовой типологии. До интеграции согласовать наглядный результат, затем внедрять в текущую оболочку небольшим модулем.

Сценарий: Сегодня → «Что заметили?» → необязательные эмоция/тело/время → подтверждение → карточка записи → список/цепочка → следующая уместная задача.

Уточнения после ввода необязательны. «Пока не знаю» и отсутствие интенсивности доступны явно. Исправить названия/статусы F02/F05, не менять старые факты. Форма ощущений имеет одно основное сохранение, корректные цвета и keyboard semantics.

Приёмка: обе темы; 390/768/1440px; RU/EN/ES; клавиатура; reduced motion; пустые/загружаемые/ошибочные состояния; сохранённая запись доступна без понимания устройства графа. Ссылка после сохранения открывает тот же record_id.

## Пакет D. NeuroMap и Путь

Приоритет P1, зависит от B/C.

- Зафиксировать семантику: исходник, отдельное появление, общее понятие, пользовательская связь, гипотеза системы.
- Сохранить историю и archive_kind. Не реконструировать точный порядок там, где его нет.
- Режим записи, повторений и исследования используют один адаптер данных.
- Список исходников, поиск, период, видимый сброс фокуса; открытие карточки не пересоздаёт раскладку.
- Воспроизвести пустую область Пути и потерю нахождения последней записи; измерить координаты/масштаб до исправления.
- Убрать безусловную интерпретацию «состояния» из недостаточных данных; показывать основание сводки.

Приёмка: 1/20/200/2000 записей, повтор одного понятия в разных сессиях, несколько мест тела у ощущения, неизвестная история, отсутствие WebGL, touch/keyboard. Сверка количества исходных записей и появлений до/после. 3D не блокирует текстовую историю.

## Пакет E. Курсы, знания и результаты

Приоритет P1/P2, зависит от B.

- Попытка практики — отдельная запись; курс хранит прогресс, не перетирая историю повторений.
- Контент урока объясняет смысл и действие; результат связывается с попыткой и наблюдением.
- Библиотека/личные заметки/источники имеют явные типы, версии и обратные ссылки.
- Профиль подключается через версионируемый адаптер, не через копирование временной типологии.

Приёмка: повтор практики в два разных дня; возврат к незавершённому ответу; происхождение каждой показанной оценки; отсутствие курса/доступа; удаление/исправление в пределах политики истории; восстановление после сбоя. Отдельно согласовать методику тестов.

## Пакет F. Коллективные пространства и окружение

Приоритет P2; зависит от A/B.

- Правила личного/семейного/командного пространства; явное «поделиться» на уровне записи.
- Проверки специалиста, ребёнка и взрослого без предположения, что членство даёт доступ ко всему.
- Внешнее поле: актуальность, источник и применимость; гипотезы влияния отдельно от измерений.
- Внутреннее поле: 2D-ввод, 3D-справочник, пояснение происхождения связей, lazy loading.

Приёмка: два аккаунта и разные пространства, отзыв доступа, неверный target, закрытая комната, недоступный внешний провайдер, устаревшие данные. Для сенситивных записей не использовать production как тестовый стенд.

## Пакет G. Один канал устройства и одна XR-практика

Приоритет P2/P3, зависит от стабильного B/E; не задерживает улучшение веб-интерфейса.

- Выбрать устройство по реальным API и возможности тестирования; отдельно определить фоновые метрики и живой поток.
- Сохранить оригинал, время, качество и подтверждённую привязку к DOM-пользователю; защищённый ingress и повтор без дубля.
- Одна XR-сцена: запуск программы, доступный ввод, результат в том же журнале. Затем проверять совместную сессию.
- Для настоящей синхронизации состояния сцены отдельно проектировать transport, reconnection и authority. Наличие WebRTC-чата не доказывает готовность XR.

Приёмка: настоящий девайс/гарнитура, повторная доставка, обрыв связи, reconnect, контроль разрешений, измеренная задержка. Без оборудования статус остаётся «не проверено».

## Решение о замене движка

Отдельный эксперимент внутри D: сравнить существующий renderer и Cytoscape на одном наборе DOM. Если текущий renderer обеспечивает читаемость, стабильность и бюджет, сохранять. Если проигрывает — заменить renderer за адаптером без переписывания наблюдений и истории. React Flow оценивать отдельно для редактирования программ. Не устанавливать все кандидаты одновременно.

## Релиз и откат

Каждый пакет: свежий main → отдельный worktree → PR с конкретными сценариями → совместимость старого клиента/API → релиз → проверка production revision. Общие файлы не заменять старой полной копией. У миграций — проверенный backup/restore и план остановки/отката. Сначала additive-contract, затем переключение потребителя; старые записи удалять только отдельным согласованным процессом.

Косметический rollback не исправляет уже повреждённые данные: проверки восстановления и сверка обязательны до миграции. Не смешивать этот выпуск с независимой работой над типированием.

## Следующий конкретный шаг

Пакет A: тестовая среда и роль клиента с программой; параллельно детальный проект operation_id/record_id пакета B и кликабельный сценарий C на синтетических данных. Перед техническим внедрением C нужен обозримый прототип, а не перечень обещанных эффектов. Готового нового прототипа этим аудитом не заявлено.
