## Общие файлы и совместимость

- Главная не меняет личный кабинет; работа над типированием не редактирует оформление и содержание главной без отдельной задачи пользователя.
- Новые стили и скрипты типирования изолировать своими файлами/корневым классом, а не глобальными правилами для всех `button`, `h2`, `.container` и т. п.
- Общие файлы (`assets/styles.css`, `assets/redesign.css`, `assets/scripts.js`, словари `data/i18n/*.json`, общие схемы профиля/API, `sw.js`) менять минимальным diff. Новые ключи локализации добавлять по месту; не заменять весь словарь устаревшей копией.
- Не менять значения/смысл общих показателей молча. Изменения контракта должны сохранять совместимость либо включать обновление обоих потребителей в одном проверенном выпуске.
- При изменениях API и миграций проверить текущую схему и предусмотреть совместимость с уже опубликованным frontend.

## Выпуск на сайт

1. В своей ветке сохранить небольшой связный блок изменений и проверить его.
2. Подтянуть свежий `main` и объединить с ним свою ветку. При конфликтах сохранить обе независимые доработки, затем повторить относящиеся к ним проверки.
3. Предпочтительно открыть PR. Влить собственный diff в текущий `main`, не отправлять полную старую копию репозитория поверх новых изменений.
4. Публикации выполнять последовательно. Перед своим выпуском проверить, не идёт ли другой выпуск; если идёт — дождаться, затем обновить базу.
5. Для GitHub API: `create_tree` строить на актуальном дереве `main`, включать только изменённые файлы; обновлять ref с `expected_sha`, `force:false`. При несовпадении SHA перечитать новую голову и заново интегрировать изменения, не обходить проверку.
6. Не применять `force push`, не удалять и не откатывать чужие коммиты.
7. После успешного workflow проверить реальный домен, свою страницу и связанные общие элементы. Только затем сообщать о публикации.

GitHub Pages публикует фронтенд целиком: даже изменение только `account.html` входит в общий выпуск сайта. Для API может потребоваться отдельная публикация; не менять инфраструктуру на основании предположений.

Это согласованный рабочий протокол, а не настроенная техническая блокировка ветки или автоматический диспетчер публикаций. Отдельный чат сам по себе не гарантирует изоляцию файлов или отсутствие конфликтов.
